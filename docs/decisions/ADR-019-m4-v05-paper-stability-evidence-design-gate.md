# ADR-019: M4 v0.5 Paper Stability Evidence Design Gate

## Status

Accepted design gate (2026-08-10). This replaces the M4 v1 paper-time
evidence baseline. The v1 matrix and evidence remain historical; they cannot
be reused as v2 evidence.

## Decision

M4 Paper stability is a real-calendar operational fact, not a simulated test.
The sole v1 proof command always returned `blocked` and its readiness helper
accepted caller-selected thresholds. M4 therefore returns to a v2 design gate.

The only path to a v2 stability conclusion is:

```text
frozen PAPER deployment + approved immutable policy + dedicated JournalDB
  -> append-only signed PaperObservation records on the deployment host
  -> daily reconciliation / incident attestations
  -> PaperEvidenceImporter verifies chain, UTC-clock attestation and lineage
  -> PaperReadinessEvaluator applies fixed thresholds
  -> durable PaperReadinessReport
  -> review_preflight evidence
```

`PaperObservation` records are generated by the actual Paper deployment. Each
record binds deployment, Release, policy, account, JournalDB identity, UTC
wall-clock sample, monotonic sample, boot ID, unique decision input reference,
and previous-record hash. The deployment host signs canonical records with an
Ed25519 key whose public-key fingerprint is fixed in the deployment record.
The private key may only be supplied as `QPS_PAPER_EVIDENCE_SIGNING_KEY` on the
Paper host and must never enter a strategy, broker payload, repository, or
review bundle.

The clock attestation at window start/end records UTC, monotonic value, boot
ID and an NTP-synchronised host status. A backward UTC sample, changed boot ID
without an explicit restart record, missing signature, sequence gap, duplicate
decision reference, mismatched deployment lineage, or missing daily record is
fail-closed. A restart is allowed only when a signed restart/reconciliation
record bridges the chain; it does not reset the window.

The fixed v2 minimum is 14 consecutive UTC calendar days and 200 independent
decisions. An independent decision is a distinct persisted `input_snapshot_ref`
for the frozen active Release, with a distinct canonical decision event; replay
of the same input, duplicate intent, or synthetic backfill cannot increase the
count. The window may exceed either threshold but cannot combine records from
different deployment, Release, policy, account, or JournalDB lineages.

Each UTC day needs a signed reconciliation result covering orders, fills,
positions, balances, funding and JournalDB ledger residuals. It also needs a
signed incident attestation: UNKNOWN, rejected order, stale data, storage
failure, runtime crash, reconciliation residual and operator finding must be
recorded with status and resolution reference. A window passes only if no P0/P1
is unresolved at its end; an unresolved P0/P1, missing attestation, or manual
evidence editing prevents readiness.

The importer persists only append-only canonical records and a derived report.
Repeated identical imports are idempotent; different content for a known ID,
UPDATE/DELETE, missing segments, altered signatures, altered source log, or
changed public key fail closed. The validator is allowed to return exit 77 only
while a real window is incomplete. It must return nonzero failure for invalid
or tampered evidence, never convert either condition to `passed`.

## Non-goals

- No real exchange API, credentials, funds, or M5 Live behavior.
- No multi-strategy allocation, crossing, netting or M6 ledger semantics.
- No automatic capital increase, unfreeze, approval, deployment, or promotion.
- A successful Paper window is operational safety evidence, not profitability
  proof or a substitute for M5 sandbox/Live acceptance.

## Consequences

M4 v2 must add the typed Paper evidence contract, dedicated journal persistence,
host collector/importer and fail-closed CLI/runner. All v1 proofs are retaken
under `M4-v05-trading-kernel-paper-v2`; no v1 passed result is copied.
