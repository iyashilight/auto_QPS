# 07 实施指南与验收标准

> 适用：项目负责人 + 开发者。定义 M0~M6 的开发顺序、每个阶段的交付物与验收标准（怎么算「写完」）。
> 最后更新：2026-08-02

## 1. 总体原则

1. **按端口契约开发**：先实现 `core/ports` 接口定义（空实现占位），再逐模块实现；禁止先写实现后补接口；
2. **测试先行**：每个模块交付必须带测试（单元/契约/集成），验收以测试通过 + 演示命令跑通为准；
3. **里程碑内闭环**：每个阶段结束时系统可运行、可演示，不允许「代码写了一半」交付；
4. **依赖方向**：core → infra → data/broker → research/trading → control，按此顺序集成；
5. **改动留痕**：接口/字段变更必须同步更新对应文档（docs/01~06）与架构文档。

### 验收标准

- [ ] 全链路集成测试：Bar → Intent → Portfolio → Risk → Execution → Paper Broker → 回报 → 持仓更新；
- [ ] 风控拦截测试：超仓位/超亏损/超频规则各自触发 BLOCK 且写入 RiskEvent；
- [ ] 重启恢复测试：Paper 运行中杀掉进程，重启后订单/持仓/风控状态一致，恢复前冻结交易；
- [ ] 多策略测试：2 个策略同标同向 → 合并订单；反向 → 按配置对冲；
- [ ] 生命周期：Validated → Paper Trading 迁移需证据且人工确认；缺证据被拒；
- [ ] Paper 连续运行 24h：无状态丢失、无未处理异常。

### 验收标准

- [ ] 契约测试：实盘 Broker 与 Paper Broker 通过同一套契约用例；
- [ ] 幂等测试：模拟网络重试，`client_order_id` 重复提交不产生双单；
- [ ] 对账演练：人为制造持仓差异，reconcile 检出并给出建议；
- [ ] Kill Switch 演练：冻结后无新订单、在途订单撤单、恢复需人工确认；
- [ ] 小资金、多策略组合（≥2 个策略）、低频率实盘运行 1 周无异常，对账一致；
- [ ] 密钥泄露检查：日志与实验记录中无密钥痕迹。

## 9. 集成顺序（合并主干顺序）

```
M0: core + infra 合入
  ↓
M1: data 合入（研究可用数据）
  ↓
M2: research 合入（可跑第一个回测）
  ↓
M3: optimizer 合入
  ↓
M4: trading(paper) 合入（完整模拟闭环）
  ↓
M5: broker(exchange) 合入（实盘闭环）
  ↓
M6: agents 合入
```

每个里程碑合入前必须：文档更新 + 测试全绿 + 演示命令跑通 + 代码评审。

## 10. 风险提示（开发期）

- **别提前做**：Web 控制台、多交易所、云部署、付费数据、HFT 基础设施（架构 §0.2 明确不做）；
- **别绕接口**：发现「图省事直接调内部实现」的 PR 一律打回；
- **别动契约**：接口签名/字段/事件类型修改必须走文档修订，不能静默改；
- **确定性优先**：回测任何非确定性（时间、随机、并发顺序）都要显式注入，不许碰运气。
